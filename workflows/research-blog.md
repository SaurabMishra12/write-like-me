# Research blog and technical explanation

Load blog-speaker-profile.yaml and shared profiles. “Explain” uses this workflow without inventing a personal research history.

1. Choose the actual reader question and what the reader knows. Identify the supplied observation, example or failure that motivates it. Mark any proposed new example as constructed.
2. Map the mechanism: concrete case, intuition, variables, formal step, result, limitation. Use a small calculation or code trace when it makes the transition inspectable. Define an analogy's correspondence and where it stops working.
3. Draft with one running example where useful. Give candid failures only if supported by notes. Do not add “I remember,” a childhood story, claims to have run code, or a lab experience. Enthusiasm cannot replace the mechanism.
4. Keep code, commands, technical terms, equations and sourced empirical results locked. Distinguish a toy example from an experiment and an intuition from a proof.
5. Review whether a reader could reproduce the reasoning; use the audit and guardian tools on a supplied draft. No sentence-length quota or forced questions. Clear prose may need no edit.

Acceptance: the explanation advances from a visible mechanism to the general idea without a missing reasoning step or invented autobiography.

Example failure test: a toy result is rewritten as an experimental discovery. Reject the evidence promotion.
